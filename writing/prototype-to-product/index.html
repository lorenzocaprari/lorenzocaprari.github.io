A prototype proves it can work. A product proves it keeps working.

Lorenzo Caprari · draft, November 2026

The demo works. The vehicle drives the loop, the robot finds the shelf, the tool finds the log line. Everyone in the room saw it, and someone is already asking when it ships.

A prototype answers one question: can this work? A product has to answer different ones. Does it keep working on hardware you don't own, with inputs you never imagined, in the hands of people you'll never meet, after the next hundred changes? Most of the code is the same. What it's held to is not.

The gap is rarely closed by a rewrite. It's closed by a sequence of steps, and the order matters more than any single step, because each one makes the next one safe. Do them out of order and paying off technical debt quietly produces new debt.

1. Write down what the prototype proved

Before touching the code, write one page. What did the prototype actually demonstrate, and under which conditions? Which inputs, which hardware, which load, for how long? Then the harder half: what did it not prove? Every prototype rests on assumptions that were reasonable for a demo, like a clean sensor, a quiet network or a single user, and that won't hold in the field.

The same page should say which parts are meant to survive and which are scaffolding. Teams lose months polishing code that was always going to be thrown away, and months more trusting code that was never meant to last.

2. Make the build boring

Nothing else is trustworthy until two machines build the same thing from the same commit. Prototypes are usually built on one laptop, with whatever compiler, libraries and flags happened to be installed. That's fine for a demo and fatal for a product: you can't reproduce a field bug if you can't rebuild the binary that shipped.

A boring build means a pinned toolchain, dependencies resolved from a lockfile through a package manager such as Conan or vcpkg, the configurations written down as CMake presets rather than remembered, and the whole thing runnable in a container. If the product targets more than one platform, cross-compilation belongs here too, not later. Adding a second target after the code has grown around one is far more painful than starting with two.

Your story here: modernising the build system of an autonomous-driving stack: what the build looked like before, what it took to cross-compile for Linux and QNX on x86 and ARM, and what changed for the team afterwards.

3. Pin today's behaviour before changing it

The instinct is to start cleaning up. Don't, yet. First capture what the system does now, right or wrong, so you'll know when a change alters it.

Characterisation tests do this: feed the current code known inputs and record its outputs as the expected result. For system software, the best inputs are usually recordings of the real world, such as CAN logs, rosbags, sensor captures or production log files, replayed through the code at full speed. They're cheap to collect, they contain the strange cases nobody would write by hand, and they turn "I think the refactor didn't change anything" into a check that runs in seconds.

Your story here: a refactor or cleanup where replayed real-world data caught a behaviour change before it reached a vehicle or a customer.

4. Let CI hold the edges

With a reproducible build and a safety net, CI can do its job: run the checks on every change so nobody has to remember them. I've written about why that matters in a separate article; here the practical point is tiers. Fast checks run on every pull request and should finish in minutes: build, unit and characterisation tests, static analysis, sanitizers. Slow checks run on a schedule: long fuzzing campaigns, full benchmark suites, soak tests and, where there's hardware, hardware-in-the-loop runs.

The split keeps the feedback loop short enough that people wait for it instead of working around it. For nesso, a small project, the per-pull-request run covers static analysis, sanitizers, fuzzing, behaviour tests and benchmarks in ten to fifteen minutes.

5. Pay debt where it costs

Technical debt is easy to find and hard to prioritise, because almost everything in a prototype qualifies. Ugliness is a bad guide. A messy module nobody touches costs almost nothing; a slightly messy one that changes every week costs a lot.

Version control already knows where the cost is. Files that change most often and are most complex are where bugs and slowdowns concentrate:

git log --since="1 year ago" --format= --name-only -- src/ \
  | sort | uniq -c | sort -rn | head -20

Cross that list with a complexity measure, from a tool such as lizard or simply function length, and the top of both lists is where cleanup pays first. Keep the rest in a written debt register, with a sentence on what each item costs, so it's a decision rather than a guilty feeling.

6. Draw the boundaries

Prototypes grow by copying: the same parsing, the same conversion, the same error handling, written slightly differently in each place that needed it. Products need one implementation per concern, behind an interface that says what it promises.

The payoff goes beyond tidiness. When a concern lives in one place, a fix lands once, a test covers every user, and the build stops recompiling the same logic many times over. The usual candidates in system software are message and signal encoding, configuration, error reporting, time and logging.

Your story here: unifying CAN signal encoding and decoding behind one implementation across a mixed fleet: what was duplicated before, and what got simpler afterwards.

7. Ratchet, don't mandate

Turning on every warning and a strict coding standard across a prototype's codebase produces thousands of findings on day one. Teams respond by ignoring them or by switching them off again. Neither raises quality.

A ratchet works better: the bar applies to new and changed code, and the count of old findings may only go down. Warnings become errors per module as each one gets clean. Static analysis starts from a recorded baseline, and CI fails only on new findings. A standard such as MISRA C++ or the CERT rules applies to files as they're touched. Quality rises with every change, and nobody has to stop the product to get there.

target_compile_options(core PRIVATE
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall -Wextra -Wpedantic -Werror>)

8. Make it operable

A demo is watched by the people who wrote it. A product runs alone, and when it misbehaves, the only witness is whatever it recorded. Before anything leaves the lab, it should be able to say which version it is, log what it was doing in a form someone else can read, report its own health, and leave something useful behind when it crashes, such as a core dump or a minidump with symbols kept for that exact build.

For anything deployed on devices, the update path belongs here too. A product that can't be updated safely, and rolled back when an update goes wrong, turns every bug into a site visit.

9. Set budgets, not opinions

"Fast enough" is an opinion until it's a number. Give the critical paths explicit budgets for latency, memory and CPU on the target hardware, measure them in CI, and fail the build when a change breaks one. Budgets also settle arguments early: whether an optimisation is worth its complexity becomes a question with an answer.

The same goes for platform assumptions. nesso's release build targets a conservative x86-64 baseline and checks the CPU once at startup before choosing its AVX2 kernel, so it runs everywhere and is fast where it can be. That decision is cheap to make deliberately and expensive to discover in a support ticket.

10. Release on purpose

A release should be an event a script performs, not a ritual a person remembers. That means versioned builds produced by CI from a tagged commit, a changelog someone outside the team can read, signed artifacts, a software bill of materials listing what's inside, and a short checklist for the steps that still need a human. Each release should be reproducible later from its tag, which is only possible because of step 2.

11. Get ready to be evaluated

Market evaluation is a test the team doesn't control. Pilot users will use the product in ways nobody planned, and the question is whether you learn from it fast. Agree beforehand what a successful trial looks like, make sure field problems come back with enough data to reproduce them, keep documentation good enough that a new user can start without you in the room, and decide who answers when something breaks. Where the domain requires it, such as functional safety for vehicles or machinery, find out early which standards apply. Certification is far cheaper to design for than to retrofit.

Your story here: a field trial or customer evaluation: what the lab never showed, and how quickly the team could reproduce and fix it.

What I'd avoid

The big rewrite. It throws away the one thing the prototype has that a new codebase doesn't: behaviour that has already met reality. Most rewrites ship late and rediscover the same bugs.

Polishing what might be thrown away. Step 1 exists so effort goes into the parts that will survive.

Process before a safety net. Reviews, standards and checklists are worth having, but without a reproducible build and tests behind them, they mostly add friction.

The order is the method

None of these steps is new on its own. What makes them work is the sequence: a reproducible build makes tests trustworthy, tests make refactoring safe, CI makes the checks automatic, and only then do standards, budgets and releases stop being paperwork. A prototype proves it can work. Each of these steps is part of proving that it keeps working.
