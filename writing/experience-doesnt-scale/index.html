Experience doesn't scale. CI does.

Lorenzo Caprari · 14 November 2026

Every team has someone who just knows. They glance at a change and say "that'll break the release build", and they're right. They remember why that timeout is 300 milliseconds, which module nobody touches on a Friday, and which warning is harmless. In a young codebase, this person is the quality process.

And it works. That's the trap.

Experience lives in one head

Experience is pattern recognition built over years of watching things break. Nothing replaces it. But however good the person is, it has three limits.

It's local. It only acts on the changes that person happens to see. As the code and the team grow, that share keeps shrinking, while everyone still behaves as if they saw everything.

It's tired. Judgement is sharp at ten in the morning on a small diff and much less sharp at seven in the evening on a large one.

It's silent. Most of what an experienced engineer knows isn't written down anywhere. It leaves when they change teams, and nobody who joined last month can check against it.

So experience grows with the number of experienced people, while risk grows with the amount of code. Those two lines cross sooner than anyone expects. After that, the team is still moving, but nobody knows what's holding.

Regressions breed regressions

Picture development without automated checks. You change something, something else breaks, and you fix it. The fix breaks a third thing, so you fix that too. Each correction makes sense on its own, but together they add up to motion without progress. Most of the effort goes into undoing yesterday's side effects.

That's what a large codebase without continuous integration (CI), automated checks that run on every change, feels like. It isn't building, it's bumping: bouncing from one break to the next, like a car with no guardrails. Everyone is busy and the code keeps growing, but the product barely moves forward.

The bill arrives in the field

Skipping tests, CI and profiling doesn't remove that work. It moves it to the most expensive place there is: the field.

A bug that a test would have caught in seconds shows up on a customer's site weeks later. Someone connects remotely, or travels, to reproduce a failure that only happens on that machine, with that data, under that load. A slowdown nobody profiled becomes "it feels sluggish since the last update", and no one can say which change caused it. The fix ships in a hurry, without checks, and plants the next problem.

That's how good engineers end up in permanent firefighting. Not because they're careless, but because every problem is found where it costs the most, and nothing stops it from coming back. Real-world validation should confirm that the product works, not be where you find out it doesn't.

CI is guardrails, not a gate

People often describe CI as a gate, something that stops you. Guardrails is a better picture.

Guardrails on a mountain road don't slow you down. They're why you can drive at a decent speed without staring at the edge. You stop worrying about falling off and think about where you're going.

Good CI does the same. A sanitizer means you don't have to inspect every pointer. A fuzzer means you don't have to imagine every malformed input. A repeatable benchmark means you don't have to remember how fast it used to be. The checks hold the edges, and your attention goes back to the real problem.

That only holds when the checks are fast and deterministic. A forty-minute pipeline with flaky tests isn't a guardrail. It's a tollbooth people learn to drive around. So the pull-request checks stay quick, with a short, bounded fuzz run, and the slow, deep work runs at night.

This is how CI scales experience: it turns what experienced people know into checks that run on every change, including the ones they'll never see.

Guardrails don't choose the route, though. CI won't design the system for you, and it doesn't replace a good review. What it does is keep the decisions you've already made true while everything else changes.

Schrödinger code

The usual plan is to write the feature now and add the tests "when things calm down". Things never calm down.

So the code ships in a strange state. I call this Schrödinger code: until something actually checks it, it's both working and broken. It might do exactly what you meant. It might also fail now and then, on some input, under some load or with some timing nobody tried. You don't know which, and neither does anyone else. The box only gets opened in production, usually at the worst possible moment.

Writing code isn't the same as knowing it works. Tests can't prove there are no bugs, as Dijkstra pointed out long ago. What they do is narrow the space where bugs can hide, and keep it narrow. That evidence isn't only for today's reviewer. It's for you in six months, when you've forgotten every detail and need to change this code safely, and for the colleague who inherits it. Without it, they aren't changing your code, they're guessing.

So the check is part of the feature, not a chore for later. Say I add a small parser for key=value lines:

// parse.hpp
#include <optional>
#include <string_view>

struct Field { std::string_view key, value; };

std::optional<Field> parse_field(std::string_view line);

In the same change, it gets a fuzz target:

// fuzz_parse.cpp: built with AddressSanitizer, runs on every pull request
#include "parse.hpp"
#include <cstddef>
#include <cstdint>
#include <functional>

extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    std::string_view input(reinterpret_cast<const char*>(data), size);
    if (auto field = parse_field(input)) {
        // Whatever the input, both views must point inside it.
        auto in_bounds = [input](std::string_view sv) {
            if (sv.empty()) return true;
            constexpr std::ranges::less_equal le{};
            const char* begin = input.data();
            const char* end = begin + input.size();
            return le(begin, sv.data()) &&
                   le(sv.data(), end) &&
                   sv.size() <= static_cast<std::size_t>(end - sv.data());
        };
        if (!in_bounds(field->key) || !in_bounds(field->value))
            __builtin_trap();
    }
    return 0;
}

AddressSanitizer catches the parser reading memory it shouldn't. The bounds check catches the quieter bug: returning a view outside its input, before any caller touches it. Once it runs in CI, nobody has to keep the rule in their head, and the guardrail goes up with the road.

AI makes the gap wider

AI coding assistants changed the speed. Someone can now produce in an afternoon what used to take a week. But the people who understand the system haven't become faster at reviewing. The gap between how much code gets written and how much is actually understood is growing, and that gap is exactly where Schrödinger code lives.

Without checks, more speed just means more bumping. With them, speed actually takes you somewhere.

I'm the person this is about

I work on nesso, a small open-source tool, mostly on my own and with help from AI agents. Its CI runs static analysis, sanitizers, fuzzing, behaviour tests and benchmarks on every pull request, and the whole run usually finishes in ten to fifteen minutes. For a one-person project, that can look excessive.

It isn't, because I'm exactly the person this article describes. I have experience, and I know it won't catch everything. A fuzzer running under AddressSanitizer found an out-of-bounds offset in nesso's parser that I'd never have spotted by reading the code. I didn't need to be smarter. I needed a guardrail.

Start with one rail

Pick the mistake your team keeps making, and turn it into a fast check on every pull request. Then write each new piece of code together with its check.

Every check is a piece of someone's experience that no longer needs them in the room. That's what scaling looks like.
